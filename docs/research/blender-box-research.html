Blender Box should drive an owned Windows host over SSH

The default run starts on the developer machine, crosses the Tailnet over SSH, and executes inside a logged-in Windows desktop that has Blender installed. blendersessiond stays on the Windows host and owns the Blender process tree.

Build a new orchestrator, not a larger daemon

blendersessiond already solves the dangerous job on the Blender machine: launch one exact process tree, install the pinned MCP add-on, allocate a loopback port, report process plus socket health, and stop only what it owns. Blender Box should own SSH, Windows setup checks, payload transfer, the interactive Scheduled Task bridge, run evidence, and cleanup.

Decision: separate repository and binary. Default remote Windows adapter. SSH alias resolves through Tailscale. No exposed MCP port.

Remote by default

The normal command runs from a repo checkout on the developer machine. It stages declared files over SSH and runs the same-machine daemon on Windows.

SSH is not the GUI launcher

Windows OpenSSH launches children in the wrong desktop session. SSH triggers a passwordless task registered for the logged-in interactive user. That task starts the daemon.

Tailscale stays replaceable

Blender Box accepts a safe SSH config alias. Tailnet DNS or a Tailscale address supplies reachability today. LAN, another VPN, or a bastion can replace it without changing Scenario config.

The current base

The daemon is small, tested, and useful. It is not a run system. That is a good starting point, not a deficiency to erase.

What is already strong

  • Named Sessions with independent ports, logs, and durable records.
  • Health means both process alive and add-on socket answering.
  • PID plus process start-time checks resist PID reuse.
  • POSIX process groups and Windows Job Objects contain owned trees.
  • Factory startup plus a pinned, telemetry-removed BlenderMCP add-on.
  • Raw Blender Python execution and viewport screenshot capture.
  • Explicit unsaved-change reporting. Stop never saves.

What a Stall still needs

  • Run IDs, accepted-run records, ordered events, history, and retention.
  • Declared payload staging into clean per-run directories.
  • Per-run Blender user config, scripts, extensions, and data roots.
  • Scenario Result JSON, outputs, validators, and failure evidence.
  • Exact session fencing across later stop, screenshot, and attach calls.
  • Scenario timeouts longer than the current 180-second wire ceiling.
  • Full-window or desktop proof in addition to a rendered viewport.
  • Kept failed Sessions with expiry and safe later cleanup.
  • Safe SSH command construction, bounded transfer, and reconnect behavior.
  • A passwordless interactive Scheduled Task plus read-only setup checks.
  • A shared Host Lock that covers every repo and controller using the Windows desktop.

Product boundary

The client owns the run from the repo checkout. The Windows adapter owns remote files and the desktop bridge. blendersessiond still runs beside Blender and keeps its same-machine contract.

The first real run

One command should prove an add-on, scene tool, geometry operation, render, or UI workflow on the remote Windows desktop. A run is not complete until evidence returns to the client and remote cleanup is known.

Accept

Create a Run ID and first ledger event before config validation. Early failures still get a small evidence manifest.

Plan

Load the named Scenario and operator Host Config. Resolve declared paths, the SSH alias, Blender requirements, transfer manifest, and evidence policy without touching the host.

Preflight

Reach Windows through the configured SSH alias. Confirm the interactive user is logged in, verify the task definition, run remote doctor, and reject any unexpected MCP listener.

Lock and stage

Acquire the shared Windows Host Lock. Create a clean run root, transfer only declared payload files, and create isolated Blender user directories. Use SFTP or a bounded archive over SSH.

Start interactively

Write a validated request JSON, then trigger the static Scheduled Task. The task runs as the logged-in user, sets the per-run environment, starts blendersessiond, publishes the exact Session identity, and polls that same Session to healthy process and socket state before calling it. The client replays only the identical fenced start request while identity is absent. Terminal or released receipts permanently reserve their Run ID. If host publication is interrupted after daemon launch, settlement adopts the opaque identity from Run-isolated daemon state before exact stop.

Execute

Use SSH to invoke blendersessiond call on Windows. A small wrapper loads the staged Scenario, exposes result and output paths, and records uncaught exceptions in the Scenario Result.

Capture and return

Capture viewport, Blender window, optional Windows desktop, final render, scene copy, logs, and Scenario Result. Hash files on Windows, transfer them back, then verify the local hashes.

Validate and settle

Run validators locally. Stop the exact remote Session by default, clean the remote run root, and release the Host Lock. Keep on failure only when requested. Finalize evidence after cleanup is known.

Viewport proof

Use the existing offscreen get_viewport_screenshot call. It captures scene appearance without relying on desktop compositing.

Window proof

Use Blender's bpy.ops.screen.screenshot for the full Blender window. Keep host desktop capture as an optional second source for OS dialogs.

Render proof

Let the Scenario write final renders to declared output paths. Record renderer, device, frame, dimensions, path, and SHA-256 beside the file.

Python helper

A tiny optional package should write result JSON with status, summary, assertions, measurements, and output paths. It must also be easy to write the JSON directly, since Blender ships its own Python.

Add-on installation

The Scenario owns install, enable, load, and behavioral assertions for its add-on. Blender Box supplies isolated roots and declared paths. It should not learn every add-on's setup convention.

Network configuration

The user config selects the normal Host Config, so run needs no transport flag. Host Config stores a safe SSH alias, not a Tailnet IP or Tailscale credential.

The Windows host contract

The remote default adds two host-side mechanisms around the daemon. The daemon itself still needs only focused identity, timeout, and capture improvements.

LandedExact public Session identity

blendersessiond start and status JSON return an opaque session_id. Call and stop require --expect-session-id. A stale Run cannot stop a newer Session that reused the same name.

LandedBounded long Scenario calls

blendersessiond call --read-timeout accepts 1 through 3,600 seconds. Blender Box carries the declared bound while the Run deadline remains authoritative.

ImplementedInteractive task bridge

Explicit setup installs one static task that calls blender-box host run-request against a fixed state root. It uses LogonType=Interactive, limited rights, no trigger, IgnoreNew, and no execution time limit. SSH atomically writes the fenced request, then starts the task.

ImplementedHost Lock and request fence

Windows stores shared host authority bound to the Run ID, controller, deadline, request hash, task name, and returned Session identity. Host mutations use an OS-released lock, and stale clients cannot replace or clean a newer Run. The typed Run request must use the exact Session name derived from its Run ID, keeping launch and settlement routing identical. After each daemon boundary, bounded reconciliation reacquires the lock, revalidates the exact authority, and durably records a deadline race as timed-out. Failed identity publication rolls back under the reconciliation deadline; if rollback also fails, settlement adopts the receipt identity only when Run-isolated daemon recovery returns the exact same value. Settlement takes the daemon executable from the controller-selected target and derives the Session name from the Run ID, so task-writable state cannot redirect the SSH controller process. It reconciles physical authority rather than trusting receipt cleanup flags and marks an interrupted active Run terminal failed. Exact stop re-observes the settled receipt so a Session identity recovered during startup cleanup is included in the public result.

P1Capability and version report

Add package version, add-on pin, server pin, capture support, and supported call features to doctor --json. Remote preflight can then reject the wrong host before staging.

P1Window screenshot helper

Expose a first-class full Blender window capture or document a stable execute_code recipe around bpy.ops.screen.screenshot. Keep it separate from the existing offscreen viewport image.

Read-only Windows check

The implemented first check streams one bounded read-only inspection over SSH. Slice 0 requires the declared SSH controller, logged-in console user, and interactive task to resolve to one Windows SID. It verifies declared executable and work-root access, trusted physical path authorities, explicit mutation authority, runtime state under sealed parents, and the complete root task action, principal, management and launch authority, settings, and security descriptor. Task authority accepts generic-all or the equivalent concrete FullControl mask emitted by Windows descriptor canonicalization. A bounded, non-launching capabilities --require blender-box-v1 --require-capability typed-call-error-reason probe rejects a daemon that lacks exact Session identity fencing, bounded call support, or typed read-timeout failures; its output goes directly to the Windows null device. A package version is not used as authority because the required contract changed without a distinguishing release version. Blender versions, stale Host Locks, and unexpected listeners remain later preflight work.

Explicit setup apply

The implemented command is plan-only unless --apply is present. Apply requires the work root and daemon to be provisioned, rejects empty input and executable-path collisions, and verifies that the authenticated SSH controller and interactive task resolve to the same SID before mutation. It validates existing physical path components and controller-only ancestor replacement authority, then guards mutation with the same OS-released operation lock used by Runs. While locked it refuses an active Host Lock, revalidates any existing host destination as a regular non-reparse file, and fails closed if the root or an existing managed entry still grants untrusted write, delete, permission, or ownership authority before path-based mutation. It then secures the declared root, creates and seals the required state directories parent-first, rehashes and atomically publishes the helper, applies matching ACLs, proves the daemon contract without launching Blender, removes exact staging files, and registers the exact interactive task. Managed executables must use a dedicated directory outside the reserved runs and receipts trees. The shared identity owns the root, state entries, executable directories, and managed files with explicit FullControl update authority. Readiness proves those effective rights and requires both state directories. The task DACL gives the same identity management and launch authority needed for repeat apply. The helper and separately hash-verified setup program use SCP; only a small bounded guard uses stdin. This avoids the proven large-stdin and command-length limits of Windows OpenSSH. Setup does not install Blender, change Tailscale, change sshd, edit the firewall, store a password, or launch Blender. Separate controller and task identities remain deferred until reparse-safe staging, publication, evidence reads, and cleanup land as one boundary.

Bounded transport grammar

The implemented setup validates its target before SSH and keeps compatibility with legacy SCP by restricting the work root to an ASCII drive path with no spaces or remote-shell syntax, enforced again by the upload adapter. Target validation reserves the exact 44-character generated setup suffix, so every accepted root remains uploadable, and reserves the longest 46-character replacement suffix after the host executable. Apply transfers a private immutable snapshot of the bytes it bounded and hashed rather than reopening a mutable build path. Blender paths outside the work root may still contain spaces. Setup and inspection seal both OS-released lock files as regular non-reparse files. The launch fence remains held until exact Session identity publication; ambiguous start errors preserve or recover that identity for exact cleanup. If a publication rollback stop succeeded but its response was lost, settlement proves the launch fence is free and repeats the exact idempotent stop. Run cleanup rejects reparse and non-regular descendants while walking bottom-up. The daemon process-output cap allows three times the decoded 1 MiB Scenario Result plus fixed headroom for Python's worst-case nested JSON escaping.

Focused daemon changes landed

  • Start and status expose the opaque Session identity; Blender Box publishes it before polling that exact Session to healthy process and socket state.
  • Call and stop require the expected exact Session identity.
  • Call accepts a bounded read timeout through 3,600 seconds.
  • Per-run Blender user roots can enter through the environment inherited at start.
  • Raw execute_code can run a small staged-script wrapper.
  • Viewport capture already writes a file and reports its method.

Do not add to the daemon

  • Repo config or payload staging.
  • Scenario Result parsing and validators.
  • Evidence Bundles, review comments, or artifact stores.
  • SSH, Tailscale, Scheduled Tasks, Host Locks, queues, TLS, or a Control Plane.
  • Generic test semantics or add-on-specific assertions.

Manifest facts

Repo revision and dirty-file hashes, config hash, declared payload, safe host alias, task name, Blender and daemon versions, Session identity, start time, and evidence policy. Do not record Tailnet addresses.

Capture facts

Source, remote and local SHA-256, requested time, completed time, media type, dimensions, render frame, capture method, and the exact Session identity.

Cleanup facts

Stopped, kept, expired, disconnected, or cleanup-failed. Record unsaved state before stop, remote workspace cleanup, and Host Lock release separately.

Build order

The safest path is a thin SSH-to-Windows slice through one real Blender add-on Scenario. Do not start with a Control Plane or a host pool.

slice 0

Windows transport spike

Reach one Windows host through its Tailscale-backed SSH alias. Prove check-only setup, shared Host Lock, payload transfer, the interactive task, exact Session identity, a long Scenario call, evidence return, and exact stop.

slice 1

Remote Windows runner

Ship init, windows check, windows setup, plan, doctor, run, status, attach, stop, history, validators, evidence, keep-on-failure, and expiry.

slice 2

Review proof

Add filesystem Evidence Store publishing, artifact manifest, PR-ready Markdown, and GitHub review-comment dry-run. Keep storage adapters thin.

slice 3

Host pool

Add an outbound Host Agent, capability reports, and a durable queue only when a second owned Windows host exists. Keep the direct SSH mode for development and recovery.

Failure gates for slice 0

  • A stale Run cannot stop a replacement Session.
  • Blender runs in the logged-in Windows desktop, not the OpenSSH service session.
  • One run cannot see another run's installed add-on or preferences.
  • A dropped SSH connection leaves a recoverable Run ID and Host Lock.
  • A timeout still produces failure evidence and a known cleanup state.
  • A screenshot names whether it is viewport, Blender window, or desktop.
  • A stopped dirty scene remains byte-for-byte unchanged unless the Scenario explicitly saved a copy.

Definition of a credible v1

  • A consuming repo owns one useful real Scenario.
  • A client machine runs it against one owned Windows host over the Tailnet.
  • The Windows user is logged in and the task definition passes read-only checks.
  • Reviewers can inspect a complete local Evidence Bundle after a remote failure.
  • Every destructive action checks exact run and Session ownership.
  • Default tests use fake SSH, task, daemon, and Blender boundaries. Protected proof uses the real host.

Decisions worth recording

These are the load-bearing choices. Write the ADRs before implementation spreads their assumptions through the code.

Keep blendersessiond same-machine

Blender Box invokes the daemon on Windows over SSH. The MCP add-on remains loopback-only and no tunnel is needed for normal Scenario calls.

Tailscale supplies reachability

Host Config contains a safe SSH alias. It does not contain Tailnet addresses or Tailscale credentials. Network choice stays outside Scenario config.

SSH cannot launch the GUI directly

A static passwordless Scheduled Task starts Blender as the logged-in interactive user. Setup is dry-run by default and changes only declared Blender Box paths and the task.

The Windows host owns the lock

A repo-local lock cannot coordinate another repo or controller. The shared Host Lock lives in the operator-managed Windows work root.

Fresh runs get isolated user roots

--factory-startup only skips the user's startup.blend. It does not replace user config, scripts, extensions, or data directories.

One run owns one Session identity

Names are routing labels. They are not enough authority for stop, screenshot, attach, or cleanup.

Scenario scripts own domain truth

Blender Box provides common file, JSON, numeric, hash, mesh-fact, and visual checks. Add-on behavior remains in the consuming repo.

Evidence has explicit capture types

An offscreen viewport image proves scene pixels. A Blender window image proves UI chrome. A host desktop image can prove OS dialogs. Do not blur them into one screenshot claim.

No generic DCC core yet

Maya Stall and Blender Box can share vocabulary and file formats. Extract code only after both products prove a stable common contract.
